= Red Hat Automotive Suite

== Overview
The https://github.com/rhadp[Red Hat Automotive Suite (RHAS),window=_blank] is an integrated development environment for
automotive software. It enables automotive software development teams to develop, test, and deploy applications
targeting the xref:intro-rhivos.adoc[Red Hat In-Vehicle Operating System (RHIVOS)], using modern cloud-native practices
built on https://www.redhat.com/en/technologies/cloud-computing/openshift[Red Hat OpenShift,window=_blank].

RHAS combines a set of tools on one OpenShift cluster:

- *Platform infrastructure* - Red Hat OpenShift, single sign-on with the Red Hat build of Keycloak, and OpenShift GitOps,
  which deploys and maintains the platform components. The *Red Hat Automotive Suite* sign-in page you log in with
  belongs to this single sign-on.
- *Red Hat OpenShift Dev Spaces* - the cloud development environment (CDE): your workspace in the browser.
- *Jumpstarter* - hardware-in-the-loop (HIL) testing: access to virtual and physical test devices, for you and for the pipelines.
- *RHAS Builder* - RHIVOS image builds with the Automotive Image Builder, as a service on OpenShift. You use it with the
  `caib` (Cloud Automotive Image Builder) command.

In this lab, you work with three of these tools: you open your workspace in Dev Spaces, lease a device with
Jumpstarter, and list and follow image builds with `caib`. Your instructors show how Red Hat OpenShift Pipelines ties
them together to build and test every change automatically.


== Solution architecture

RHAS covers the complete software lifecycle as a continuous loop of four stages:

image::rhas/01-architecture.png[]

. **Development** - Cloud-based development environments in
  https://developers.redhat.com/products/openshift-dev-spaces/overview[Red Hat OpenShift Dev Spaces,window=_blank],
  optionally organized by https://developers.redhat.com/rhdh/overview[Red Hat Developer Hub,window=_blank].
. **Integration** - https://www.redhat.com/en/technologies/cloud-computing/openshift/pipelines[Red Hat OpenShift Pipelines,window=_blank]
  builds and tests every change, https://www.redhat.com/en/products/trusted-application-pipeline[Red Hat Trusted Application Pipeline,window=_blank]
  secures the software supply chain, and a container registry stores the results. This lab uses the OpenShift internal registry.
. **Deployment and delivery** - https://jumpstarter.dev/[Jumpstarter,window=_blank] deploys the software to test devices;
  device management delivers it to production.
. **Targets** - The software runs on virtual devices, on physical devices, and finally in the vehicles of a fleet.
  Feedback from the targets flows back into development.

NOTE: This lab covers development, integration, and deployment to test devices. Developer Hub, telemetry, and fleet
delivery are not part of it.

== From source code to the device

Building software for RHIVOS follows the same basic steps, whether you do it by hand or fully automated:

// Diagram redrawn after slide 4 of the RHAS system architecture deck.
.Generic RHIVOS development workflow
image::rhas/03-rhivos-workflow.svg[Generic RHIVOS development workflow: app source code, secure build, container or RPM, Automotive Image Builder, OS image, virtual and physical device]

. *Application build* - Your application source code is compiled in a secure build against the RHIVOS headers and libraries.
  The result is packaged as a container image or an RPM package.
. *OS build* - The *Automotive Image Builder* takes a *target OS manifest*, which describes what goes into the image, and
  combines your container or RPM with the RHIVOS packages into a bootable *OS image*.
. *Deployment* - The OS image is deployed to a *virtual device* for fast feedback, and later to a *physical device*.

The Red Hat Automotive Suite automates this flow on OpenShift:

// Diagram redrawn after slide 5 of the RHAS system architecture deck.
.Generic automotive app development workflow
image::rhas/04-app-workflow.svg[Generic automotive app development workflow: code repository, app and OS build pipelines, artifact store, Jumpstarter flashing a virtual machine or a device under test]

. A developer commits code to a repository or opens a merge request.
. An *app build pipeline* builds the application into a container image or RPM and stores it in an *artifact store*,
  such as a container registry.
. An *OS build pipeline* uses the Automotive Image Builder to compose the application and the OS into an image,
  which is stored in the artifact store as well.
. *Jumpstarter* takes the image from the artifact store and flashes it onto a virtual machine or a physical device under
  test (DUT, often an SoC board).

In this lab, you follow the lower half of this flow: you take an image that the pipeline has already built, flash it
onto a virtual machine with Jumpstarter, and look inside. In the last activity, you walk back through the manifest and
the pipeline that produced it. The upper half, a code change that runs through the pipeline, is shown by your
instructors on the projector, and so is the same image on a real ARM SoC board.
