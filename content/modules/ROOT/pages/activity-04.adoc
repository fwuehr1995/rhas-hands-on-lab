= Testing and Validation

== Overview

While Red Hat OpenShift Dev Spaces provides a consistent environment for developing, building, and testing automotive applications, comprehensive validation 
requires testing on virtual or physical hardware. This additional testing ensures:

- System stability
- Performance optimization
- Compatibility across target platforms

Before building a production-ready RHIVOS image, you must verify that your application functions correctly in a cloud environment. 

After that, you can build a RHIVOS image with the modified application embedded, preparing it for end-to-end testing in
virtualized hardware environments using Jumpstarter.

NOTE: The following activity builds upon activity "Application Development", where you modified the application code.

[#test-app]
== Enable tests

Before committing your changes to the source code repository, you need to enable some test cases 
that will be run against the application later in the pipeline.

IMPORTANT: Open `tests/test_on_hardware.py` and remove the three code annotations.

image::app/14-enable-test.png[]

The code should look like this when you are done:

image::app/14-enable-test-done.png[]

Before removing the code annotations, the test cases only covered the RHIVOS image, verifying that it is booting correctly.
The additional test cases test the radio application itself.

The first test is to check if the container image of the apps is present:

[source,python]
----
    def test_podman_images(self, client):
        with client.console.pexpect() as console:
            console.sendline("podman images")
            console.expect_exact("]#", timeout=10)
            assert "localhost/app" in console.before.decode()
----

The second test is to check if the radio app is running as a system service:

[source,python]
----
    def test_radio_service(self, client):
        with client.console.pexpect() as console:
            console.sendline("systemctl status --no-pager radio.service")
            console.expect_exact("]#", timeout=10)
----

The third test is to interact with the radio service, and see if it can change the volume.

[source,python]
----
    def test_radio_service_interaction(self, client):
        with client.console.pexpect() as console:
            console.sendline("podman exec -i systemd-radio radio-client")
            console.expect_exact("Connecting to radio service", timeout=10)

            # test changing volume
            console.sendline("+" * 10)
            console.expect_exact("Volume:  [#####################]", timeout=10)
            console.sendline("-" * 10)
            console.expect_exact("Volume:  [                     ]", timeout=10)
            console.sendline("+" * 5)
            console.expect_exact("Volume:  [##########           ]", timeout=10)

            console.sendline("q")
            console.expect_exact("]#", timeout=10)
----

[#manifest]
== The image manifest

The contents of the RHIVOS image are declared in `manifests/auto-app.aib.yml`. Open it in the editor.

The manifest lists the RPM repositories to pull from, the packages to install, directories to create,
and files to inject into the image:

[source,yaml]
----
repos:
  - id: alex
    baseurl: https://download.copr.fedorainfracloud.org/results/alexl/cs9-sample-images/centos-stream-9-$arch/
    priority: 10
  - id: local
    baseurl: file:///workspace/src/bin
    priority: 5
rpms:
  - auto-app
  - podman
  - qm
  - openssh-server
  - dlt-daemon
  - dlt-tools
  - greenboot-default-health-checks
  ...
----

Your application is delivered as a systemd Quadlet unit, injected through the `add_files` section:

[source,yaml]
----
add_files:
  - path: /etc/containers/systemd/engine.container
    text: |
      [Unit]
      Description=Demo engine service container
      Requires=routingmanagerd.socket

      [Container]
      Image=localhost/auto-apps
      Volume=/run/vsomeip:/run/vsomeip
      Exec=/usr/bin/engine-service

      [Service]
      Restart=always

      [Install]
      WantedBy=multi-user.target
----

NOTE: File contents are written inline with `text:`. The alternative `source_path:` form, which copies a
file from the workspace into the image, is documented but currently fails to locate the file both locally
and in the pipeline. Use the inline form.

== Commit and push your changes

Committing to the repository is all it takes to start a build — a webhook on the repository triggers the
pipeline on every push.

IMPORTANT: Click the *Source Control* button in the left sidebar to open the source control tab.

IMPORTANT: In the input box, put `"add new radio station"` as the commit message, then click *Commit*.

image::app/17-commit.png[]

IMPORTANT: Click the *Sync Changes* button to push your commit to the repository.

image::app/18-push.png[]

NOTE: If no pipeline run appears within a minute, push again. The webhook occasionally misses the first
push of a session.


[#pipeline]
== The build pipeline

The push triggers a Tekton `PipelineRun` named `pr-build-validate-<id>`.

IMPORTANT: Open the OpenShift console and switch to the *Developer* perspective, then select *Pipelines*.

https://console-openshift-console.{openshift_cluster_ingress_domain}[window=_blank]

TIP: Your pipeline runs in the project `buildspace-<username>-rhas-starter`, where `<username>` is the
account you registered in the first activity.

image::starter/12-pipeline-run.png[]

Looking at the pipeline in detail, it performs the following tasks:

- `setup-jmp`: Prepares the Jumpstarter configuration used by the later tasks.
- `clone-repo`: Clones the repository at the commit you just pushed.
- `setup-workspace`: Prepares the build workspace.
- `get-lease`: Requests and waits for a Jumpstarter Exporter lease. The leased device is used for testing in the following tasks.
- `build-rpm`: Builds your application into an RPM package.
- `build-os`: Builds the RHIVOS image from `manifests/auto-app.aib.yml`, with your RPM included.
- `flash`: Flashes the new image to the leased device.
- `validate`: Runs the test cases from the `tests` directory against the running device.
- `cleanup`: Ends the lease and returns the device to the pool.

This is the point of the Automotive Suite: the same pipeline that validates against a virtual QEMU device
can target real hardware. Swap the Exporter and every change is tested on the physical ECU, inside the
normal development cycle.


[#reflash]
== Flash and verify the new image

When the pipeline has finished, your new image is available from the build service.

[source,sh,role=execute]
----
caib image list
----

The newest entry is the image the pipeline just built. Copy its URI, then lease a device and flash it
exactly as you did in the previous activity:

[source,sh,role=execute]
----
jmp shell -l device=qemu
----

[source,sh,role=execute]
----
DISKIMAGE=<paste the URI here>
j flasher flash oci://$DISKIMAGE
j power on && j console start-console
----

After logging in, confirm your application is present in the qm partition:

[source,sh,role=execute]
----
podman exec -it qm bash
----
