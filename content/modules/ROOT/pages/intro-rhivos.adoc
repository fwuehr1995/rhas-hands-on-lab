= Red Hat In-Vehicle Operating System

== Overview
https://www.redhat.com/en/blog/new-standard-red-hat-vehicle-operating-system-modern-and-future-vehicles[Red Hat In-Vehicle Operating System (RHIVOS),window=_blank]
delivers a Linux-based foundation for the software-defined vehicle, enabling cloud-native development, functional safety, and long-term relevancy.
It is the operating system that the Red Hat Automotive Suite targets: with the suite, you develop and test applications
for RHIVOS and build complete RHIVOS OS images.

RHIVOS is built around three principles:

- **Open** - Developed in the open, based on proven enterprise Linux technology.
- **ASIL-B** - Designed for functional safety and certified according to ISO 26262 ASIL-B.
- **Secure** - Built with the security practices you know from Red Hat Enterprise Linux.

RHIVOS is the commercial product from Red Hat. Its upstream open source variant is the
https://sigs.centos.org/automotive/[CentOS Automotive Stream Distribution (AutoSD),window=_blank],
which is developed by the CentOS Automotive SIG. In this lab, you may come across both names.

== Tailored to the automotive industry

RHIVOS is tailored to meet the specific demands of the automotive industry:

- **Package selection** - All RHEL packages and automotive-specific packages are included.
- **Hardware architecture** - A wide variety of hardware platforms based on the aarch64 and x86 architectures is supported.
- **Safety certification** - Certified according to ISO 26262 ASIL-B as a Safety Element out of Context (SEooC).
- **Fast boot** - Optimized startup times for automotive applications.
- **Real-time capabilities** - Reduced variation and preemptive latency, with PREEMPT-RT enabled by default.
- **Mixed-criticality support** - Host multiple concurrent workloads at different integrity levels on the same system.
- **Diverse use cases** - From digital cockpits and ADAS to gateways, and from QM up to ASIL-B applications.
- **Modern software development** - Embrace containers and DevOps for agile build-test-deploy cycles.

== Containers on wheels: mixed criticality

Mixed criticality and containers are what this lab is about. With RHIVOS, automotive applications are delivered as
containers, just like applications in the data center, and a RHIVOS image is split into two partitions:

- The *root partition*, also called the ASIL partition, runs the safety-relevant workloads.
- The *QM partition* runs workloads that are only quality-managed (QM), such as infotainment.

Whatever an application in the QM partition does, even if it crashes, hangs, or takes all the CPU time, nothing may
happen to the safety-relevant applications in the root partition. This guarantee is called *freedom from interference*.

The QM partition is itself a container. The operating system separates it from the root partition with the same
mechanisms that isolate containers in the data center: separate process namespaces, resource limits, and SELinux
labels. The only connections between the partitions are the ones that were configured on purpose.

== The demo application

The image you boot in this lab runs a small demo application, split across both partitions:

.Demo applications in the partitions of a RHIVOS image
image::rhas/05-partitions.svg[Root partition with the engine service and a DLT daemon, QM partition with the radio service, routing manager, DLT daemon, and the sysbench load generator, connected through shared sockets in /run/ipc]

- The *engine service* simulates the drivetrain. It is safety-relevant and runs in the root partition.
- The *radio service* simulates the infotainment radio. When the vehicle reverses, it must turn its volume down, so that
  warning sounds can be heard. It runs in the QM partition.
- The *routing manager* passes messages between them, using the SOME/IP protocol over shared sockets. Only applications
  with the right SELinux label may use these sockets.
- *sysbench* is a benchmark tool in the QM partition. Started on demand, it tries to keep all CPU cores busy, like a
  runaway application would. The radio service in the QM partition suffers from it, the engine service in the root partition
  does not.

In the lab activities, you boot this image, look at the applications from each side, watch the radio turn itself down
when the vehicle reverses, put the QM partition under full CPU load, and find out how the image was built with the *Automotive Image Builder*.
