= Exploring the System

== Overview

The image you just booted runs a small set of demo automotive applications, all delivered as containers:

- The *engine service* simulates the vehicle's drivetrain and periodically switches between driving and reversing.
  It is safety-relevant, so it runs in the *root partition* (the ASIL partition).
- The *radio service* simulates an infotainment radio. It is not safety-relevant, so it runs in the *QM partition*.
  When the vehicle reverses, the radio must turn its volume down, so that warning sounds can be heard.
- The *routing manager* connects the services. They talk to each other using https://some-ip.com/[SOME/IP,window=_blank],
  a communication protocol widely used in vehicles, implemented by the vsomeip library.

In this activity, you stay in the root partition and look at the system from there, and into the QM partition. Then you
find out what allows the engine in the root partition to talk to the radio in the QM partition, and what stops
everything else. Finally, you put the QM partition under full CPU load, and watch the radio struggle while the engine
keeps running.

NOTE: You should still be logged in on the serial console of your device, with the prompt `[root@auto-app ~]#`.
If you are not, or if your one-hour lease has expired in the meantime (the console disconnects and you are back at the
`(venv) sc-demo (main) $` prompt), go back to the previous activity and lease, flash, and boot the device again.


[#rootpartition]
== The view from the root partition

Containers in the root partition are managed by Podman, controlled by systemd. List the running containers:

[source,sh,role=execute]
----
podman ps
----

You should see four containers:

[source,sh]
----
CONTAINER ID  IMAGE                         COMMAND               CREATED         STATUS         PORTS     NAMES
571c80d0ee36  localhost/ffi_server:latest   ffi-server            36 seconds ago  Up 36 seconds  7001/tcp  ffi_server
1b0e4c2f7a93  localhost/auto-apps:latest    /usr/bin/dlt-daem...  36 seconds ago  Up 36 seconds            systemd-dlt
7105b825a991                                /sbin/init            36 seconds ago  Up 35 seconds            qm
e3b72595c8e0  localhost/auto-apps:latest    /usr/bin/engine-s...  4 seconds ago   Up 4 seconds             systemd-engine
----

- `systemd-engine` is the engine service, running from the `auto-apps` container image.
- `qm` is the whole QM partition. It is a container too, running its own init system (`/sbin/init`).
- `systemd-dlt` is a logging daemon. DLT is the standard logging format in automotive systems.
- `ffi_server` belongs to a memory test that is not part of this lab. You can ignore it.

Now list the container images these containers were started from:

[source,sh,role=execute]
----
podman images
----

[source,sh]
----
REPOSITORY            TAG     IMAGE ID      CREATED                 SIZE    R/O
localhost/auto-apps   latest  020e7433bb03  Less than a second ago  271 MB  true
localhost/ffi_server  latest  94667235a236  Less than a second ago  231 MB  true
----

There is no image for the `qm` container. The QM partition is not pulled from a registry at run time: the Automotive
Image Builder builds it into the OS image, together with the root partition. Combining both partitions into one
bootable image is the core of what the image builder does. The `R/O` column shows that the application images are
read-only too: they are part of the OS image, not downloaded later. You will see in the next activity where this is
configured.

The engine service runs as a systemd service named `engine`. Follow its log:

[source,sh,role=execute]
----
journalctl -f -u engine
----

Every second, the engine reports how its computing work went. Every few seconds, it switches gear and allocates a
little memory:

[source,sh]
----
... ENGINE: CPU demo metrics: target_cpu=300ms actual_cpu=300.0ms wall=300.0ms ... misses_total=0
... ENGINE: CPU demo metrics: target_cpu=300ms actual_cpu=300.0ms wall=300.1ms ... misses_total=0
... ENGINE: Driving...
... ENGINE: RAM demo: requested=10.0MiB result=OK ...
... ENGINE: CPU demo metrics: target_cpu=300ms actual_cpu=300.0ms wall=300.0ms ... misses_total=0
----

- `target_cpu` is the CPU time the engine needs per cycle, `actual_cpu` the CPU time it got, and `wall` how long the
  cycle took in real time. When `wall` stays close to `actual_cpu`, the engine never had to wait for the CPU.
- `misses_total` counts the cycles in which the engine missed its deadline. Keep an eye on it: it should stay at `0`
  for the whole lab.

  service, run as `qm_container_ipc_t`. The routing manager of the root partition runs directly on the host, as
  `vsomeip_t`. Keep these labels in mind, you will need them in a moment.


[#qmpartition]
== A look into the QM partition

The QM partition is a container, so you reach it with Podman. You do not need to log in to it: you run commands inside
it directly from the root partition, with `podman exec qm` in front of the command.

The QM partition runs its own Podman with its own containers. List them:

[source,sh,role=execute]
----
podman exec qm podman ps
----

[source,sh]
----
CONTAINER ID  IMAGE                       COMMAND               CREATED        STATUS        PORTS  NAMES
edc9600baeb5  localhost/auto-apps:latest  /usr/bin/radio-se...  8 minutes ago  Up 8 minutes         systemd-radio
a8b28d50a0c0  localhost/auto-apps:latest  /usr/bin/dlt-daem...  8 minutes ago  Up 8 minutes         systemd-dlt
2e131385d7c1  localhost/auto-apps:latest  /usr/bin/routingm...  7 minutes ago  Up 7 minutes         systemd-routingmanagerd
----

Here you find the radio service, the DLT logging daemon, and the routing manager of the QM partition. They use the same
`auto-apps` container image as the engine service in the root partition.

[#radio]
=== Listen to the radio

The radio has a small client to control it. Start the client inside the running radio container:

[source,sh,role=execute]
----
podman exec -it qm podman exec -it systemd-radio radio-client
----

The outer `podman exec` enters the QM partition, the inner one enters the radio container inside it.

WARNING: The `-it` flags are required on both commands, because the radio client is interactive. Without them, the
client does not start correctly.

The client shows what the radio is playing:

[source,text]
----
Radio Los Santos
Everyday
Trouble feat. Gucci Mane
VOL [##########----------] 50%
> FWD | R:+ | E:+
+/- Volume  SPACE Station  ESC Power  M Monitor  Q Quit
----

- The first three lines are the station, the song, and the artist. `VOL` is the volume.
- The status line shows the driving direction that the engine reports, `> FWD` for driving and `< REV` for reversing,
  followed by the health of the radio (`R:`) and of the engine (`E:`). `+` means healthy.
- The last line lists the keys of the client.

NOTE: You will not hear anything. The radio does not play audio. It simulates the work of an infotainment system:
decoding multimedia data takes CPU time, and buffering it takes memory.

Press *+* a few times to turn the volume up, and press *SPACE* to switch to another station. Then wait a few seconds
and watch the volume.

Whenever the engine service in the root partition switches to reverse, the status line shows `< REV` and the radio
turns its volume down on its own, here from 50% to 30%:

[source,text]
----
Radio Los Santos
Everyday
Trouble feat. Gucci Mane
VOL [######--------------] 30%
< REV | R:+ | E:+
+/- Volume  SPACE Station  ESC Power  M Monitor  Q Quit
----

When the engine switches back to driving, the status line shows `> FWD` again and the volume returns to where it was.

This is the whole demo application at work: the safety-relevant engine service in the root partition tells the radio
service in the QM partition that the vehicle is reversing, through the routing manager.

TIP: The *M* key opens an interference monitor. You will use it at the end of this activity.

IMPORTANT: Press *Q* to quit the radio client.

[#radiolocal]
=== Try the same client from outside the container

The radio client is also installed directly in the QM partition. Start it there, outside the radio container, with
only one `podman exec`:

[source,sh,role=execute]
----
podman exec -it qm radio-client
----

This time the client cannot reach the radio:

[source,sh]
----
RADIO UNAVAILABLE
Waiting for radio service
Last title:
VOL --
? DIR | R:OFF | E:OFF
+/- Volume  SPACE Station  ESC Power  M Monitor  Q Quit
----

The client starts, but it receives nothing: no title, no volume, no direction, and both the radio (`R:OFF`) and the
engine (`E:OFF`) are off as far as it can tell.

IMPORTANT: Press *Q* to quit the client. If it does not return to the `[root@auto-app ~]#` prompt, press *Ctrl+C*.

After you quit, the start-up messages of the vsomeip library appear:

[source,text]
----
... [info] Using configuration file: "/etc/vsomeip.json".
... [info] Parsed vsomeip configuration in 0ms
... [info] Configuration module loaded.
... [info] Security disabled!
... [info] Initializing vsomeip (3.5.11) application "Radio client".
... [info] Instantiating routing manager [Proxy].
... [info] vsomeip tracing not enabled. vsomeip service discovery tracing not enabled.
... [info] Application(Radio client, 1002) is initialized (11, 100).
----

There are no errors: the client initializes normally, but it never gets a connection to the routing manager.
`Security disabled!` refers to the optional access control built into vsomeip itself, which this demo does not use.
The barrier here is SELinux.

It is the same program, in the same partition. The difference is the permission to use the sockets that the services
communicate over. Started inside the radio container, the client runs with the `qm_container_ipc_t` label you saw
earlier. Started directly in the QM partition, it does not get that label, and it is not allowed in. This is not a
bug, it is one of the security mechanisms of the platform at work.

[source,sh]
----
F   UID   PID  PPID PRI  NI    VSZ   RSS WCHAN  STAT TTY   TIME COMMAND
4     0     1     0  20   0  21352 12396 ep_pol Ss   ?     0:00 /sbin/init
4     0    26     1  20   0  33444 10032 ep_pol Ss   ?     0:00 /usr/lib/systemd/systemd-journald
...
4     0    96    92  20   0 257692  7508 ep_pol Ssl  ?     0:00 /usr/bin/radio-service
4     0    97    93  20   0   3172  2352 poll_s Ss   ?     0:00 /usr/bin/dlt-daemon
...
4     0   124   122  20   0 209068  8052 ep_pol Ssl  ?     0:00 /usr/bin/routingmanagerd

----

The picture is very different:

- You only see the processes of the QM partition. The engine service and everything else in the root partition are invisible.
- The QM partition has its own PID namespace: its own init system runs as PID 1, and the process IDs differ from the ones you saw in the root partition.

This is the isolation that makes mixed criticality possible. The root partition can observe and control the QM partition,
but workloads in the QM partition cannot see or interfere with the safety-relevant workloads in the root partition.


[#ipc]
== How the partitions talk to each other

If the partitions are isolated, how does the engine tell the radio that it is reversing? The only connection between them
is the one that was configured on purpose: a shared directory with communication sockets. List it:

[source,sh,role=execute]
----
ls -l /run/ipc/
----

[source,sh]
----
total 0
drwxrwxrwt. 2 root root 100 Oct 23 00:00 dlt
srwxrwxrwx. 1 root root   0 Oct 23 00:00 ffi_server.socket
drwxrwxrwt. 2 root root 120 Oct 23 00:09 vsomeip
----

// TODO(dry run): confirm the permissions of ffi_server.socket in the current image.

`ffi_server.socket` belongs to the memory test that is not part of this lab. The `vsomeip` directory holds the sockets
for the SOME/IP communication:

[source,sh,role=execute]
----
ls -l /run/ipc/vsomeip/
----

[source,sh]
----
total 0
srw-rw-rw-. 1 root root 0 Oct 23 00:00 vsomeip-0
srw-rw-rw-. 1 root root 0 Oct 23 00:00 vsomeip-101
srw-rw-rw-. 1 root root 0 Oct 23 00:00 vsomeip-103
--w-------. 1 root root 0 Oct 23 00:00 vsomeip.lck
----

`vsomeip-0` belongs to the routing manager, which coordinates the communication. The other sockets belong to the
services connected to it, such as the engine and the radio.

Now the SELinux labels from the beginning of this activity make sense:

- The containers in the root partition run as `ipc_t`, and the containers in the QM partition, such as the radio
  service, run as `qm_container_ipc_t`. These labels allow them to use the sockets in `/run/ipc`.
- Everything else in the QM partition runs as `qm_t`, without access to the sockets. That is why the radio client
  failed when you started it outside the radio container.

Check that SELinux actually enforces its policy on this system:

[source,sh,role=execute]
----
getenforce
----

[source,sh]
----
Enforcing
----

Like a production RHIVOS system, this image runs SELinux in *enforcing* mode: every access that the policy does not
allow is blocked. The access rights to the communication between the partitions are not a matter of convention: they
are part of the image and enforced by the operating system. The socket file permissions (`srw-rw-rw-`) alone would let
anybody in; SELinux is the layer that decides.

[#ffi]
== Freedom from interference: full CPU load in the QM partition

Isolated processes are one part of freedom from interference. The other part is resources: a misbehaving application
in the QM partition must not be able to take CPU time away from the safety-relevant applications in the root partition.

The demo applications are built to show this. The engine service and the radio service each do a fixed amount of
computing work all the time, just like real control and infotainment software. You will see in the next activity where
this load is configured. In addition, the QM partition contains the benchmark tool `sysbench` as a service. It tries to
keep all CPU cores of the device busy, like a runaway application would.

NOTE: This section takes about 5 minutes. All virtual devices of this lab share the same cluster, so run `sysbench` only
while you watch its effect, and always stop it again at the end.

[#tmuxsetup]
=== Split the console

You need to watch the radio client and type commands at the same time. A short script splits the serial console into
two panes with `tmux`, which is installed on the device. Copy the whole block and paste it into the serial console:

[source,sh,role=copypaste]
----
SESSION=autosd-demo
tmux new-session -d -s $SESSION -n "Autosd Demo"
tmux split-window -v -t $SESSION:0
tmux send-keys -t $SESSION:0.0 "podman exec -it qm podman exec -it systemd-radio radio-client" C-m
tmux send-keys -t $SESSION:0.1 "# podman exec qm systemctl start sysbench" C-m
tmux select-pane -t $SESSION:0.1
tmux attach-session -t $SESSION
----

The script creates a tmux session with two panes, one above the other:

- The *upper pane* runs the radio client.
- The *lower pane* is where you type. It shows the command that starts the load as a comment (`#`), as a reminder of
  what comes next. A comment does nothing when it runs.

You are in the lower pane. To work in the other pane, press *Ctrl+B* and then an arrow key: *Up arrow* for the upper
pane, *Down arrow* for the lower pane.

WARNING: Press *Ctrl+B* only once before each key. Pressing *Ctrl+B* three times in a row quits the Jumpstarter serial
console. The essential tmux keys are also on the xref:cheatsheet.adoc#tmux[Cheatsheet].

NOTE: Inside tmux, the radio client is shown without colors. This does not affect the demo.

[#cpubaseline]
=== Open the interference monitor

The radio client has a built-in monitor that shows how well the radio service and the engine service get their work
done.

. Press *Ctrl+B*, then the *Up arrow* key, to move to the upper pane.
. Press *M* to open the monitor.
. Press *Ctrl+B*, then the *Down arrow* key, to move back to the lower pane.

Below the radio display, the monitor shows one column for the radio service and one for the engine service:

[source,sh]
----
INTERFERENCE MONITOR  (M to close)
                     RADIO           ENGINE
Service              AVAILABLE       AVAILABLE
CPU                  NORMAL          NORMAL
RAM                  NORMAL          NORMAL
Data link            EVENTS SEEN     EVENTS SEEN
Last event           0.0s ago        1.1s ago
CPU share            99.7%           100.0%
Deadline overrun     0.0ms           0.0ms
Allocated RAM        768 MiB         10 MiB
Direction            --              REV
Health age           0.0s ago        1.1s ago
Health sequence      390             324

CPU/RAM from SOME/IP health; (demo) = metadata fallback; -- = no measurement
----

Both services report their health over SOME/IP, through the same routing manager and sockets as the rest of the demo.
The rows mean:

[cols="1,3",options="header"]
|===
| Row | Meaning
| Service | Whether the service is reachable over SOME/IP: `AVAILABLE` or `UNAVAILABLE`.
| CPU | `NORMAL` while the service gets the CPU time it needs, `DEGRADED` when it does not.
| RAM | `NORMAL` while the service gets the memory it asks for.
| Data link | `EVENTS SEEN` while the messages of the service arrive regularly, `DEGRADED` when they are late.
| Last event | How long ago the last message from the service arrived.
| CPU share | The share of real time in which the service actually got the CPU while doing its work. 100% means it never had to wait.
| Deadline overrun | How much the service exceeded the deadline of its work cycle. `0.0ms` means it finished every cycle in time.
| Allocated RAM | The memory the service holds for its work: the radio keeps a buffer for multimedia data, the engine needs very little.
| Direction | The driving direction the engine reports: `FWD` or `REV`. The radio has no direction of its own (`--`).
| Health age, Health sequence | The age and the running number of the last health report. The number keeps increasing while the service is alive.
|===

In the last line, `(demo)` marks a value taken from the configuration of the demo instead of a measurement, and `--`
means that there is no measurement.

[#cpuload]
=== Put the QM partition under load

In the lower pane, start `sysbench` in the QM partition:

[source,sh,role=execute]
----
podman exec qm systemctl start sysbench
----

TIP: Instead of pasting the command, you can press the *Up arrow* key to fetch the comment line from the history,
press *Ctrl+A* (or *Home*) to jump to the start of the line, delete the `#` and the space, and press *Enter*.

After a few seconds, watch the radio in the upper pane. The radio service no longer gets enough CPU time to do its
work. The display turns garbled, and the monitor shows the difference between the two services. With the worst overlaps removed, it looks
like this:

[source,text]
----
H?o!l*d ~U#p
M~arion #Band$ @feat. N%ipsey &Hussle
> FWD | R:+ CPU! | E:+
INTERFERENCE MONITOR  (M to close)
                     RADIO           ENGINE
Service              AVAILABLE       AVAILABLE
CPU                  DEGRADED        NORMAL
RAM                  NORMAL          NORMAL
Data link            DEGRADED        EVENTS SEEN
CPU share            86.0%           100.0%
Deadline overrun     0.3ms           0.0ms
...
----

NOTE: The monitor itself runs in the QM partition, so its display gets garbled too: lines shift or overlap. Look for
the `CPU`, `CPU share`, and `Deadline overrun` rows.

- The radio column changes: `CPU` and `Data link` switch to `DEGRADED`, the CPU share drops below 100%, and deadline
  overruns appear. The status line shows `CPU!` next to the radio health.
- The engine column does not change: `CPU` stays `NORMAL`, the CPU share stays at 100%, and there is no deadline
  overrun. The direction still switches between `FWD` and `REV`.

This is what freedom from interference means for CPU time. `sysbench` and the radio service both run in the QM
partition, so they compete with each other for the CPU time of the QM partition, and the radio loses. The engine service
in the root partition keeps its CPU time: the load in the QM partition does not spread to the safety-relevant
applications.

TIP: To see the competition from the operating system's side, run `top` in the lower pane. `sysbench` appears near the
top of the list, and the radio service gets much less CPU time than the engine service. Press *q* to quit `top`.

[#cpustop]
=== Stop the load

In the lower pane, stop `sysbench`:

[source,sh,role=execute]
----
podman exec qm systemctl stop sysbench
----

The command takes a few seconds to return. Shortly afterwards, the radio display is clean again, and the radio column
of the monitor returns to `NORMAL`.

Check that the engine service kept its schedule the whole time. This shows its log of the last 10 minutes:

[source,sh,role=execute]
----
journalctl -u engine --since "-10 min" --no-pager
----

The timestamps run without gaps, right up to now, and `misses_total` is still `0`.
