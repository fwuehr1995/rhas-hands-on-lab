= Exploring the System

== Overview

The image you just booted runs a small set of demo automotive applications, all delivered as containers:

- The *engine service* simulates the vehicle's drivetrain and periodically switches between driving and reversing.
  It is safety-relevant, so it runs in the *root partition* (the ASIL partition).
- The *radio service* simulates an infotainment radio. It is not safety-relevant, so it runs in the *QM partition*.
  When the vehicle reverses, the radio must turn its volume down, so that warning sounds can be heard.
- The *routing manager* connects the services. They talk to each other using https://some-ip.com/[SOME/IP,window=_blank],
  a communication protocol widely used in vehicles, implemented by the vsomeip library.

In this activity, you stay in the root partition and look at the system from there, and into the QM partition. Then you
find out what allows the engine in the root partition to talk to the radio in the QM partition, and what stops
everything else. Finally, you put the QM partition under full CPU load, and watch the radio struggle while the engine
keeps running.

NOTE: You should still be logged in on the serial console of your device, with the prompt `[root@auto-app ~]#`.
If you are not, or if your one-hour lease has expired in the meantime (the console disconnects and you are back at the
`(venv) sc-demo (main) $` prompt), go back to the previous activity and lease, flash, and boot the device again.


[#rootpartition]
== The view from the root partition

Containers in the root partition are managed by Podman, controlled by systemd. List the running containers:

[source,sh,role=execute]
----
podman ps
----

You should see four containers:

[source,sh]
----
CONTAINER ID  IMAGE                         COMMAND               CREATED         STATUS         PORTS     NAMES
571c80d0ee36  localhost/ffi_server:latest   ffi-server            36 seconds ago  Up 36 seconds  7001/tcp  ffi_server
1b0e4c2f7a93  localhost/auto-apps:latest    /usr/bin/dlt-daem...  36 seconds ago  Up 36 seconds            systemd-dlt
7105b825a991                                /sbin/init            36 seconds ago  Up 35 seconds            qm
e3b72595c8e0  localhost/auto-apps:latest    /usr/bin/engine-s...  4 seconds ago   Up 4 seconds             systemd-engine
----

- `systemd-engine` is the engine service, running from the `auto-apps` container image.
- `qm` is the whole QM partition. It is a container too, running its own init system (`/sbin/init`).
- `systemd-dlt` is a logging daemon. DLT is the standard logging format in automotive systems.
- `ffi_server` belongs to a memory test that is not part of this lab. You can ignore it.

The engine service runs as a systemd service named `engine`. Follow its log:

[source,sh,role=execute]
----
journalctl -f -u engine
----

Every few seconds the engine switches gear:

[source,sh]
----
Oct 23 00:03:33 auto-app systemd-engine[697]: ENGINE: Reversing...
Oct 23 00:03:37 auto-app systemd-engine[697]: ENGINE: Driving...
Oct 23 00:03:47 auto-app systemd-engine[697]: ENGINE: Reversing...
----

NOTE: Right after boot you may also see a few `[error]` or `[warning]` lines from vsomeip. They appear while the services start up and can be ignored.

IMPORTANT: Press *Ctrl+C* to stop following the log.

Now look at all processes on the system as a tree (the `f` option), together with their SELinux security context
(the `Z` option):

[source,sh,role=execute]
----
ps axfZ
----

The output is long. Scroll to the end, where you find the containers. Shortened, it looks like this:

Two things stand out:

- From the root partition, you see *everything* that runs on the system, including the processes inside the QM
  partition: below the QM partition's own init system (`/sbin/init`) you find the radio service, a DLT logging daemon,
  and a routing manager of its own.
- Every process carries an SELinux label in the first column. The containers in the root partition, such as the engine
  service, run as `ipc_t`. The QM partition itself runs as `qm_t`, and the containers inside it, such as the radio
  service, run as `qm_container_ipc_t`. The routing manager of the root partition runs directly on the host, as
  `vsomeip_t`. Keep these labels in mind, you will need them in a moment.


[#qmpartition]
== A look into the QM partition

The QM partition is a container, so you reach it with Podman. You do not need to log in to it: you run commands inside
it directly from the root partition, with `podman exec qm` in front of the command.

The QM partition runs its own Podman with its own containers. List them:

[source,sh,role=execute]
----
podman exec qm podman ps
----

[source,sh]
----
CONTAINER ID  IMAGE                       COMMAND               CREATED        STATUS        PORTS  NAMES
edc9600baeb5  localhost/auto-apps:latest  /usr/bin/radio-se...  8 minutes ago  Up 8 minutes         systemd-radio
a8b28d50a0c0  localhost/auto-apps:latest  /usr/bin/dlt-daem...  8 minutes ago  Up 8 minutes         systemd-dlt
2e131385d7c1  localhost/auto-apps:latest  /usr/bin/routingm...  7 minutes ago  Up 7 minutes         systemd-routingmanagerd
----

Here you find the radio service, the DLT logging daemon, and the routing manager of the QM partition. They use the same
`auto-apps` container image as the engine service in the root partition.

[#radio]
=== Listen to the radio

The radio has a small client to control it. Start the client inside the running radio container:

[source,sh,role=execute]
----
podman exec -it qm podman exec -it systemd-radio radio-client
----

The outer `podman exec` enters the QM partition, the inner one enters the radio container inside it.

WARNING: The `-it` flags are required on both commands, because the radio client is interactive. Without them, the
client does not start correctly.

The client shows what the radio is playing:

[source,sh]
----
Station: Radio Los Santos
Song:    ILLuminate
Artist:  Ab-Soul feat. Kendrick Lamar
Volume:  [##########          ]
-----------------------------------------
 Usage: volume: +/-, station: SPACE on/off: ESC, quit: Q
----

Press *+* a few times to turn the volume up, and press *SPACE* to switch to another station. Then wait a few seconds
and watch the volume bar.

Whenever the engine service in the root partition switches to reverse, the client shows `[REVERSING]` and the radio
turns its volume down on its own:

[source,sh]
----
Station: Radio Los Santos
Song:    Sellin' Dope
Artist:  Freddie Gibbs & Mike Dean
Volume:  [######              ]
-----------------------------[REVERSING]-
 Usage: volume: +/-, station: SPACE on/off: ESC, quit: Q
----

This is the whole demo application at work: the safety-relevant engine service in the root partition tells the radio
service in the QM partition that the vehicle is reversing, through the routing manager.

IMPORTANT: Press *Q* to quit the radio client.

[#radiolocal]
=== Try the same client from outside the container

The radio client is also installed directly in the QM partition. Start it there, outside the radio container, with
only one `podman exec`:

[source,sh,role=execute]
----
podman exec -it qm radio-client
----

This time the client cannot reach the radio. Instead you see a stream of vsomeip warnings and errors such as:

[source,sh]
----
... [warning] cei::shutdown_and_close_socket_unlocked: socket has been reset, ...
... [error] ltcei::max_allowed_reconnects_reached: ...
... [info] Application/Client 1002: Reconnecting to routing manager.
----

IMPORTANT: If the client does not return to the `[root@auto-app ~]#` prompt by itself, press *Ctrl+C*.

It is the same program, in the same partition. The difference is the permission to use the sockets that the services
communicate over. Started inside the radio container, the client runs with the `qm_container_ipc_t` label you saw
earlier. Started directly in the QM partition, it does not get that label, and it is not allowed in. This is not a
bug, it is one of the security mechanisms of the platform at work.

[#qmps]
=== The processes inside the QM partition

Now list the processes once more, this time as the QM partition sees them:

[source,sh,role=execute]
----
podman exec qm ps axl
----

[source,sh]
----
F   UID   PID  PPID PRI  NI    VSZ   RSS WCHAN  STAT TTY   TIME COMMAND
4     0     1     0  20   0  21352 12396 ep_pol Ss   ?     0:00 /sbin/init
4     0    26     1  20   0  33444 10032 ep_pol Ss   ?     0:00 /usr/lib/systemd/systemd-journald
...
4     0    96    92  20   0 257692  7508 ep_pol Ssl  ?     0:00 /usr/bin/radio-service
4     0    97    93  20   0   3172  2352 poll_s Ss   ?     0:00 /usr/bin/dlt-daemon
...
4     0   124   122  20   0 209068  8052 ep_pol Ssl  ?     0:00 /usr/bin/routingmanagerd
...
----

The picture is very different:

- You only see the processes of the QM partition. The engine service and everything else in the root partition are invisible.
- The QM partition has its own PID namespace: its own init system runs as PID 1, and the process IDs differ from the ones you saw in the root partition.

This is the isolation that makes mixed criticality possible. The root partition can observe and control the QM partition,
but workloads in the QM partition cannot see or interfere with the safety-relevant workloads in the root partition.


[#ipc]
== How the partitions talk to each other

If the partitions are isolated, how does the engine tell the radio that it is reversing? The only connection between them
is the one that was configured on purpose: a shared directory with communication sockets. List it:

[source,sh,role=execute]
----
ls -l /run/ipc/
----

[source,sh]
----
total 0
drwxrwxrwt. 2 root root 100 Oct 23 00:00 dlt
drwxrwxrwt. 2 root root 120 Oct 23 00:09 vsomeip
----

The `vsomeip` directory holds the sockets for the SOME/IP communication:

[source,sh,role=execute]
----
ls -l /run/ipc/vsomeip/
----

[source,sh]
----
total 0
srw-rw-rw-. 1 root root 0 Oct 23 00:00 vsomeip-0
srw-rw-rw-. 1 root root 0 Oct 23 00:00 vsomeip-101
srw-rw-rw-. 1 root root 0 Oct 23 00:00 vsomeip-103
--w-------. 1 root root 0 Oct 23 00:00 vsomeip.lck
----

`vsomeip-0` belongs to the routing manager, which coordinates the communication. The other sockets belong to the
services connected to it, such as the engine and the radio.

Now the SELinux labels from the beginning of this activity make sense:

- The containers in the root partition run as `ipc_t`, and the containers in the QM partition, such as the radio
  service, run as `qm_container_ipc_t`. These labels allow them to use the sockets in `/run/ipc`.
- Everything else in the QM partition runs as `qm_t`, without access to the sockets. That is why the radio client
  failed when you started it outside the radio container.

Check that SELinux actually enforces its policy on this system:

[source,sh,role=execute]
----
getenforce
----

[source,sh]
----
Enforcing
----

Like a production RHIVOS system, this image runs SELinux in *enforcing* mode: every access that the policy does not
allow is blocked. The access rights to the communication between the partitions are not a matter of convention: they
are part of the image and enforced by the operating system. The socket file permissions (`srw-rw-rw-`) alone would let
anybody in; SELinux is the layer that decides.

[#ffi]
== Freedom from interference: full CPU load in the QM partition

Isolated processes are one part of freedom from interference. The other part is resources: a misbehaving application
in the QM partition must not be able to take CPU time away from the safety-relevant applications in the root partition.

The demo applications are built to show this. The engine service and the radio service each do a fixed amount of
computing work all the time, just like real control and infotainment software. You will see in the next activity where
this load is configured. In addition, the QM partition contains the benchmark tool `sysbench` as a service. It tries to
keep all CPU cores of the device busy, like a runaway application would.

NOTE: This section takes about 5 minutes. All virtual devices of this lab share the same cluster, so run `sysbench` only
while you watch its effect, and always stop it again at the end.

[#tmuxsetup]
=== Split the console

You need to watch the radio client and the CPU usage at the same time. Split the serial console into two panes with
`tmux`, which is installed on the device:

[source,sh,role=execute]
----
tmux
----

. Press *Ctrl+B*, then *"* (double quote). The console splits into an upper and a lower pane, and you are in the lower one.
. Press *Ctrl+B*, then the *Up arrow* key, to move to the upper pane. Start the radio client there:
+
[source,sh,role=execute]
----
podman exec -it qm podman exec -it systemd-radio radio-client
----
. Press *Ctrl+B*, then the *Down arrow* key, to move back to the lower pane.

WARNING: Press *Ctrl+B* only once before each key. Pressing *Ctrl+B* three times in a row quits the Jumpstarter serial
console. The essential tmux keys are also on the xref:cheatsheet.adoc#tmux[Cheatsheet].

[#cpubaseline]
=== Watch the normal CPU usage

In the lower pane, start `top`:

[source,sh,role=execute]
----
top
----

The engine service and the radio service are at the top of the list. Each of them keeps one CPU core almost fully busy:

[source,sh]
----
    PID USER      PR  NI    VIRT    RES    SHR S  %CPU  %MEM     TIME+ COMMAND
    346 root      20   0  323192   7464   6772 S  97.7   0.1  25:36.06 engine-service
    862 root      20   0 1716020   1.0g   4556 S  97.7   8.6  23:08.55 radio-service
----

The radio client in the upper pane shows the song and the artist as usual.

Press *q* to quit `top`.

[#cpuload]
=== Put the QM partition under load

Still in the lower pane, start `sysbench` in the QM partition:

[source,sh,role=execute]
----
podman exec qm systemctl start sysbench
----

Start `top` again:

[source,sh,role=execute]
----
top
----

After a few seconds, `sysbench` appears near the top of the list, and the radio service gets much less CPU time than
before. The engine service in the root partition is not affected:

[source,sh]
----
    PID USER      PR  NI    VIRT    RES    SHR S  %CPU  %MEM     TIME+ COMMAND
    346 root      20   0  323192   7464   6772 S  97.3   0.1  26:20.33 engine-service
   1867 root      20   0   42728   5728   3696 S  54.5   0.0   0:15.63 sysbench
    862 root      20   0 1716020   1.0g   4556 S  37.5   8.6  23:35.89 radio-service
----

Now look at the radio client in the upper pane. The radio service no longer gets enough CPU time to do its work, and
the display shows garbled text:

[source,sh]
----
Station: Space 103.2
Song:    N%ight&s, F?eel !Like *Gett~in' #Down
Artist:  B*i~ll#y@ O%c&ea?n
Volume:  [######              ]
-----------------------------[REVERSING]-
 Usage: volume: +/-, station: SPACE on/off: ESC, quit: Q
----

This is what freedom from interference means for CPU time. `sysbench` and the radio service both run in the QM
partition, so they compete with each other for the CPU time of the QM partition, and the radio loses. The engine service
in the root partition keeps its CPU time: the load in the QM partition does not spread to the safety-relevant
applications. The `[REVERSING]` indicator still follows the engine, because the engine keeps working on schedule.

[#cpustop]
=== Stop the load

Press *q* to quit `top`, and stop `sysbench`:

[source,sh,role=execute]
----
podman exec qm systemctl stop sysbench
----

The command takes a few seconds to return. Shortly afterwards, the radio client shows clean text again.

Check that the engine service kept switching gears the whole time. This shows its log of the last 10 minutes:

[source,sh,role=execute]
----
journalctl -u engine --since "-10 min" --no-pager
----

The timestamps run without gaps, right up to now.

. Press *Ctrl+B*, then the *Up arrow* key, to move to the upper pane, and press *Q* to quit the radio client.
. Type `exit` in each pane to close it. When the last pane is closed, tmux ends, and you are back on the serial console
  with the prompt `[root@auto-app ~]#`.


[#leave]
== Leave the device

IMPORTANT: Quit the serial console by *pressing `Ctrl+B` three times*.

Your shell prompt changes back to `sc-demo ⚡qemu-exporter-0 ➤`. You are back in the Jumpstarter shell on your workspace.

Release the lease, so that the device is free for others:

[source,sh,role=execute]
----
exit
----

Your prompt is back to `(venv) sc-demo (main) $`.
