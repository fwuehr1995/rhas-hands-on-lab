= Exploring the System

== Overview

The image you just booted runs a small set of demo automotive applications, all delivered as containers:

- The *engine service* simulates the vehicle's drivetrain and periodically switches between driving and reversing.
  It is safety-relevant, so it runs in the *root partition* (the ASIL partition).
- The *radio service* simulates an infotainment radio. It is not safety-relevant, so it runs in the *QM partition*.
- The *routing manager* connects the services. They talk to each other using https://some-ip.com/[SOME/IP,window=_blank],
  a communication protocol widely used in vehicles.

In this activity, you look at the same system from two sides: from the root partition and from inside the QM partition.

NOTE: You should still be logged in on the serial console of your device, with the prompt `[root@localhost ~]#`.
If you are not, or if your 30-minute lease has expired in the meantime (the console disconnects and you are back at the
`(venv) sc-demo (main) $` prompt), go back to the previous activity and lease, flash, and boot the device again.


[#rootpartition]
== The view from the root partition

Containers in the root partition are managed by Podman, controlled by systemd. List the running containers:

[source,sh,role=execute]
----
podman ps
----

You should see two containers:

[source,sh]
----
CONTAINER ID  IMAGE                         COMMAND               CREATED         STATUS         PORTS  NAMES
dd383c3c2c99                                /sbin/init            12 seconds ago  Up 11 seconds         qm
8b0bfe959...  localhost/auto-apps:latest    /usr/bin/engine-s...  12 seconds ago  Up 12 seconds         systemd-engine
----

- `systemd-engine` is the engine service, running from the `auto-apps` container image.
- `qm` is the whole QM partition. It is a container too, running its own init system (`/sbin/init`).

The engine service runs as a systemd service named `engine`. Follow its log:

[source,sh,role=execute]
----
journalctl -f -u engine
----

Every few seconds the engine switches gear:

[source,sh]
----
... localhost systemd-engine[660]: ENGINE: Reversing...
... localhost systemd-engine[660]: ENGINE: Driving...
... localhost systemd-engine[660]: ENGINE: Reversing...
----

NOTE: Right after boot you may also see a few `[error]` or `[warning]` lines about `/run/vsomeip`. They appear while the services start up and can be ignored.

IMPORTANT: Press *Ctrl+C* to stop following the log.

Now look at the processes of the demo applications:

[source,sh,role=execute]
----
ps -ef | grep -E 'engine|radio|routing' | grep -v grep
----

You see the engine service, but also the radio service and the routing manager, even though those run inside the QM partition.
From the root partition, you can see everything that runs on the system, including the processes in the QM partition.

[#qmpartition]
== The view from inside the QM partition

You cannot log in to the QM partition directly. Because it is a container, you enter it with Podman:

[source,sh,role=execute]
----
podman exec -it qm /bin/bash
----

WARNING: The `-it` flags are required. Without them the command appears to succeed but leaves you in the
root partition shell rather than inside the QM partition, which is easy to miss.

Your prompt changes to `bash-5.2#`. You are now inside the QM partition.

The QM partition runs its own Podman with its own containers. List them:

[source,sh,role=execute]
----
podman ps
----

[source,sh]
----
CONTAINER ID  IMAGE                       COMMAND               CREATED        STATUS        PORTS  NAMES
a4ca2dc05...  localhost/auto-apps:latest  /usr/bin/dlt-daem...  2 minutes ago  Up 2 minutes         systemd-dlt
66c315d78...  localhost/auto-apps:latest  /usr/bin/radio-se...  2 minutes ago  Up 2 minutes         systemd-radio
5d343e699...  localhost/auto-apps:latest  /usr/bin/routingm...  2 minutes ago  Up 2 minutes         systemd-routingmanagerd
----

Here you find the radio service, the routing manager, and a DLT logging daemon (DLT is the standard logging format in automotive systems).
They use the same `auto-apps` container image as the engine service in the root partition.

Follow the radio's log:

[source,sh,role=execute]
----
journalctl -f -u radio
----

[source,sh]
----
... systemd-radio[95]: RADIO: Playing song "Still Livin'" by Freddie Gibbs (on Radio Los Santos) 50% volume
... systemd-radio[95]: RADIO: Playing song "I Can't Wait" by Young Scooter feat. Trinidad James (on Radio Los Santos) 50% volume
----

Now look at the processes again, this time from inside the QM partition:

[source,sh,role=execute]
----
ps -ef
----

The picture is very different:

- You only see the processes of the QM partition. The engine service and everything else in the root partition are invisible.
- The QM partition has its own PID namespace: its own init system runs as PID 1, and the process IDs differ from the ones you saw in the root partition.

// TODO(dry run): confirm that ps is available in the QM partition and add a sample output block.

This is the isolation that makes mixed criticality possible. The root partition can observe and control the QM partition,
but workloads in the QM partition cannot see or interfere with the safety-relevant workloads in the root partition.
The only connection between the two is the one that was configured on purpose: a shared socket directory
(`/run/vsomeip`) through which the services exchange SOME/IP messages.

NOTE: In this demo image, SELinux runs in *permissive* mode: policy violations are logged but not blocked.
A production RHIVOS system runs SELinux in *enforcing* mode, which adds another layer of protection between the partitions.


[#leave]
== Leave the device

Leave the QM partition and return to the root partition:

[source,sh,role=execute]
----
exit
----

IMPORTANT: Quit the serial console by *pressing `Ctrl+B` three times*.

Your shell prompt changes back to `sc-demo ⚡qemu-exporter-0 ➤`. You are back in the Jumpstarter shell on your workspace.

Release the lease, so that the device is free for others:

[source,sh,role=execute]
----
exit
----

Your prompt is back to `(venv) sc-demo (main) $`.
